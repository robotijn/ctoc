# Small changes take a small path — three paths chosen by measured signals at intake, and the critique fleet runs only where a human is deciding

## The human's two requests, verbatim (2026-09-30)

> "ctoc is overdoing the usage of ctoc, small changes for example an interface change do not require a complete ctoc run, ultrathink what need ctoc and what doesn't"

> "there are too many pre-mortms and way too many devils-advicate being started"

One rule answers both: **the process scales with what there is to decide and with what the change could break, not with the fact that a file changed.** Part A applies the rule to changes. Part B applies it to the critique fleet. The two parts are technically independent: Part B needs nothing from Part A and Part A needs nothing from Part B. What is built and when is the human's to choose; this plan schedules nothing.

This plan is also the explicit request to change gate logic that `CLAUDE.md` requires. The sections "Mandatory Pipeline Use (v7)" and "Human Gates" are the contract; what this plan changes in them, and what it leaves absolute, is stated in section 2 and in the settled choices under Decisions Taken Under Ambiguity. Approving this plan is the human's approval of exactly that and nothing wider. The five questions this plan first put to the human are now settled as documented choices under his instruction of 2026-09-30 (see Decisions By The Human); they are the session's choices, not options the human picked himself, and review can overturn any of them.

### 1.1 What every change costs today (read)

1. **The routing reminder sends every change to a plan.** On each human prompt in a CTOC project, `src/hooks/UserPromptSubmit.js` calls `buildReminder` in `src/lib/ctoc-routing-reminder.js`. If the prompt contains one of twelve change verbs (build, add, fix, implement, change, refactor, write, remove, update, rename, migrate, wire) and either no plan is in progress or the in-progress count has changed since the session last saw it, it injects a directive telling the session to run `/ctoc:start` and create or activate a plan "before editing any file". It closes with: "If this change is genuinely too small for a plan, say so plainly and let the human type an escape phrase." It stays silent when the prompt already contains an escape phrase. **This is the intake point that already exists, and it has one answer.**
2. **The edit hook decides each edit in this order** (`enforce` in `src/hooks/PreToolUse.Edit.js`): deny writes to the approval ledger, deny writes to the verify evidence store, deny writes to the streaming store except its quarantine; allow the whitelisted infrastructure paths (`plans/*.md`, `.ctoc/*` except the two command tables, `VERSION`, ignore files); pass silently if the project is not a CTOC project; allow if an **approved** plan in in-progress or todo declares the file (a plan for a protected enforcement file must carry a human approval, not a sufficiency crossing); allow if the human typed an escape phrase; otherwise the mode decides — `strict` blocks, `soft` warns and allows, `off` allows. Strict is the schema default and the value in this repository's `.ctoc/settings.json`; `.ctoc/settings.yaml` outranks that file and was not read.
3. **The typed escape phrases** are seven words in `src/lib/escape-phrases.js`: hotfix, trivial fix, trivial change, quick fix, urgent, skip planning, skip iron loop. They count only when the human typed them (the transcript is read role-scoped: tool results and assistant text are excluded) and only within the last 5000 characters of user-typed text. **Three separate lists of escape phrases exist:** those seven; four in the settings default (`workflow.escapePhrases` in `src/lib/settings.js`, also present in this repository's `.ctoc/settings.json`); and a different six in `src/lib/refinement-loop.js` and `.ctoc/config/refinement-triggers.yaml` (it has "skip refinement" and lacks "skip planning" and "skip iron loop"). The hooks read the first list only.
4. **The shell hook decides each Bash command in this order** (`main` in `src/hooks/PreToolUse.Bash.js`): deny an unreadable payload; deny ledger forgery; deny irreversible commands; deny raw `mv` or `cp` of plan files; load the project's signed Iron Loop state; **if the command is `git commit` or `git push`, deny unless the state's current step is at least 15**; classify what the command writes; **if the command writes, or might write (an interpreter such as `node`, or a task runner such as `npm` or `make`, classifies as "might"), deny unless the state names a feature and its current step is at least 8**; then, for commands whose write targets are determinate, ask the same plan-coverage question the edit hook asks, with the same whitelist and the same typed-phrase check, and deny an uncovered target at every mode.
5. **The two step gates are project-wide.** `getStatePath` in `src/lib/state-manager.js` keys one state file per project directory, so `feature` and `currentStep` are one pair for the whole project, shared by up to five concurrent builds. A typed escape phrase never reaches these gates: they run before the coverage stage that reads the phrase.
6. **What that adds up to.** A request that reads as a change is routed to a plan. A plan means a functional plan, the human's approval to build, an implementation plan or several, the human's approval of the approach, and steps 8 to 16 per slice. The one lighter route needs the human to type a word, and even then a commit or a test run through `npm` needs the project state to sit at the right step.

## 2. ALIGN — Approach

### The principle

Process is spent on decisions and on blast radius. A change with nothing to decide and nothing that can break outside its own diff needs the checks that catch a mistake, not the documents that record a decision. A change with a decision in it, or a consequence outside the diff, keeps today's whole pipeline unchanged.

### User stories

1. **As the human owner**, **I want** a change with nothing to decide to run only the checks that catch a mistake, **so that** a rename or a typo is finished in one exchange instead of a plan, two approvals and a build queue. (Independent of the others; testable by criteria 1 and 2.)
2. **As the human owner**, **I want** a small behaviour change to be built test-first without planning documents and then shown to me as "finished?", **so that** I still decide when it is done but I am not asked to approve a plan for it. (Criterion 3.)
3. **As the human owner**, **I want** anything on the trust boundary to take the full path whatever anyone types, **so that** making small things cheap can never make my gates cheap. (Criteria 4, 6, 12, 13, 29 and 30.)
4. **As the human owner**, **I want** to be told which path was chosen and which signal decided it, and to override in either direction with a word, **so that** the classifier advises and I stay in control. (Criteria 5, 7, 8 and 16.)
5. **As the human owner**, **I want** the critique fleet to run only where I am deciding what to build or how to build it, once for a group of slices, never twice for the same unchanged plan, and within a cap (10 per open by default) that I can change, **so that** opening the dashboard does not queue hundreds of agent runs and does not crowd out the builds. (Criteria 18 to 28.)

### Part A — three paths, chosen at intake by signals

**Never lighter than:** the full gate (`npm test`: whole suite, coverage floor read from `.ctoc/coverage-baseline.json`, zero skipped), one read of the diff by `agents/quality/code-reviewer.md` (a wrapper agent whose tools are Read, Grep and Glob, so the dispatcher supplies the diff as data), and the trust-boundary rule.

1. **Direct change.** No plan, nothing before the build. For changes with nothing to decide: a rename, a signature change where every caller is found by something that fails loudly, a type widening, a typo, a comment, formatting, a configuration value, a patch-level bump of a dependency. Runs: the tests that cover the file when the coverage map knows them, a green baseline of them before the edit so a red after is attributable, the full gate, one diff read, then the commit with the project's patch bump. The human sees an announcement line before the first edit and a milestone line at the end.
2. **Quick loop.** No planning documents; test first. For a small behaviour change inside one module whose whole specification is in the request. Runs: a failing test first, the implementation, the diff read, the full gate, and the human's "finished?" with a summary of the diff; under an active keep-going batch that becomes a status line.
3. **Full loop.** Today's pipeline, unchanged. For anything with a decision in it or a consequence outside the diff: a new module or feature (a new module must be wired, and the reachability fence checks it), more than one module changed in behaviour, a persisted format, a public interface consumed outside the repository, a migration, a deploy, a new dependency, an unanswered fork in the request, and **always** anything on the trust boundary.

"Status" is one of: **measured** (a deterministic source exists and its output is the signal), **partial** (a source exists and covers only part; the part is stated), **none** (no source; nothing is invented). **An unmeasurable signal counts as pushing up, never as green.**

**Two kinds of signal, and the difference is load-bearing.** Signals measured from the file set, and the trust boundary, are hard: code decides them. The fork statement and the "structure only" claim are asserted by a model and cannot be measured. The classifier records which is which, and **re-measures at finish from the real diff**: if the diff measures higher than the path the change started on, the change stops and reclassifies (criterion 11). An assertion is never allowed to be the only barrier.

**Other stacks.** CTOC is installed into projects of other languages. The measured sources above are the JavaScript ones on disk. In another stack the same rule applies with fewer green signals: most changes there classify quick or full, and direct is rare. No per-language measurement source is part of this plan.

### The decision rule

- **All signals green:** CTOC states the path in one line and proceeds.
- **Mixed, or a signal with no source that the request needs:** CTOC names the deciding signal and asks the human once. The two answers are "plan it" and "just do it". The question is an owner decision (how much process to spend), so it is presented flat, with the consequence of each answer in plain words and no recommendation marker.
- **Override up, "plan it":** always honoured. The path becomes full; any open light-path record is closed as superseded.
- **Override down, "just do it":** honoured for every signal except the trust boundary. Each overridden signal is recorded and shown in the announcement line. The floor above still applies.
- **The red line:** if the measured signals include the trust boundary, "just do it" is refused, with the reason stated, and the path is full. **The trust boundary is never overridden down by the classifier or by an override word, and a typed escape phrase no longer lifts it either:** decision 19 removes that phrase's power over boundary files, so one rule holds for the classifier, the override words and the seven typed phrases alike.
- **Where the words are read:** only from text the human typed, through the same role-scoped extraction the escape phrases use (`extractUserTypedText`, exported by `PreToolUse.Edit.js`) and the same word-bounded matching. A phrase in assistant text or a tool result is ignored. It is logged when the classifier reads the transcript and sees it; a phrase in prose no CTOC code reads cannot be logged, and this plan does not claim otherwise.
- **The seven typed escape phrases keep exactly today's behaviour on every file off the trust boundary.** On a trust-boundary file they are no longer consulted (decision 19). The classifier does not reinterpret them.

### What must change in the hooks, and what must not

**Where the classifier runs.** At the existing intake point: `buildReminder` in `src/lib/ctoc-routing-reminder.js` stops injecting one constant directive and injects a path-aware one: classify first (name the files you propose to change, and state any fork you see), then proceed on the path the classifier records. Silence on a typed escape phrase stays. This text is an instruction to the session, not a fence; the fence is the grant logic below, whose default when the session does not classify is today's behaviour (the edit is blocked in strict mode).

**The grant.** A light-path record is a small structured file written only by CTOC code, through one sanctioned argv-driven script, into a new directory under `.ctoc/`. It holds: an identifier; the path (direct or quick); the **exact** repository-relative file list (no globs, so the unanchored-declaration problem cannot arise); the fingerprint of the human's request text; the measured signals with their sources; any override used and any signal it overrode; and a state (open, closed by commit, closed as superseded, closed as abandoned). **No clock expiry** (no time value is invented): a record ends by commit, supersession or abandonment, and it verifies only against the transcript of the session that holds the human's message, so a new session finds an inert record. If the transcript no longer holds the message (for example after a long session is summarised; believed, not verified), the record is inert and the edit is refused as today, never allowed.

**Why the light path does not set the project-wide signed state instead.** Setting `feature` and `currentStep` would open the write and commit gates for every concurrent full-path build in the project at the same time, and a full-path build's state would silently satisfy a light-path commit. The record is per change.

**Strength, stated honestly.** The grant can be requested by an agent (the session runs the script), but it is issued by code from measurements, bound to a message the human really typed, limited to exact files, and never covers the trust boundary. It is strictly narrower than a typed escape phrase, which today unlocks any file outside three directories and, after decision 19, any file outside those three directories and outside the trust boundary. Two inputs stay asserted (the fork statement, the structure-only claim); both are re-checked at finish. The diff review is a required step whose strength equals today's review step in the full loop: self-reported by the executor, plus the human's "finished?" and the full gate. This plan does not claim more. The human's acknowledgement on the quick path is relayed by the session exactly as the existing approvals are relayed; it is no stronger than they are.

### When a light change grows

The record lists exact files, so an edit to an unlisted file is refused by the hook. The executor files the existing scope-growth question (`requestScopeGrowth` in `src/lib/scope-growth.js`, seven mandatory fields, filed in the inbox, with the continuation fork registered so stopping is legitimate). For a change with no plan the request names the record, and the tool reports `forced_by_declared` as unknown (it could not look), which is the honest value. Nothing is committed and nothing is reverted; the working-tree diff so far stays and is handed to the planner. On the human's answer the path becomes full, the record is closed as superseded, and the functional plan is created then, through the existing create-plan route. At finish the diff is re-measured with the signals above; growth inside a listed file (a new export, a new dependency) stops the change the same way.

### Human moments

- **Direct:** the announcement line before the first edit, the milestone line at the end. Nothing else unless something fails.
- **Quick:** "finished?" with the diff summary before the commit, or a status line under an active keep-going batch. **The only machine-readable "keep going" is the continuation batch** (`src/lib/continuation.js`); no code reads a typed "keep going", so this plan uses the batch and says so.
- **Full:** unchanged, including the four moments the human owns.
- **Push:** unchanged. It is surfaced as a decision, never automatic.

### Part B — the critique fleet runs only where a human is deciding what to build or how to build it

1. **Only at the two pre-build decisions, only for a plan on the full path.** A plan is a candidate only at "what to build" (functional) and "how to build it" (implementation). Never a plan in review, todo, in progress, done, vision or canvas. Todo, in progress, done, vision and canvas already hold in code; **review is removed from the candidate list by this plan** (decision 18): the human's finished decision stays exactly his, and nothing critiques it. The plan pins all of it with a test so it cannot drift. A light-path change has no plan and is never a candidate.
2. **One combined critique per parent group.** A plan's group is its `parent_plan` (read once per plan from the merged frontmatter; a plan with no parent is a group of one). The recipe runs one critique for the group. **A group is a decision point when no sibling is in an earlier stage than the one being decided** (for the approach decision, no sibling still in functional); siblings already further along do not hold the group back, and the members are the group's plans currently at the decision stage. Until the group is a decision point it is reported as not yet critiqued. Each slice can reach a stage at a different time, so critiquing on each arrival would run the fleet as many times as there are slices. The human is asked each group question once and the answer counts for every member. `listSubplans` scans every stage on each call, so the grouping must read the corpus once and group in one pass, not call it per plan.
3. **Never re-run an unchanged plan; never run twice at once.** A critique is kept while the plan's bytes are unchanged: a content fingerprint of the plan is stored with the questions and compared before a plan is made a candidate (decision 22), so a plan re-saved with identical bytes is not a candidate. The human's answers keep today's rule, unchanged: they stay bound to the modification stamps, and the sufficiency predicate and `readAnsweredQuestionIds` are not touched, so a save that changes nothing can still make the human answer the same questions again, at no agent cost. How one questions file carries its two different freshness rules is a construction detail for the implementation plan; the constraint is that the answer rule is today's, byte for byte, and that a questions file with no fingerprint (every file on disk today) is judged by today's modification-time rule. A plan with a critique already queued, running, or written and waiting in the quarantine for the next sweep is not dispatched again, for any trigger (session start or dashboard open).
4. **Which lenses.** At the two pre-build decisions the four lenses and the synthesizer stay: the recipe names all four, as the synthesizer and the advocate say they run (decision 15). At the finished decision there is no fleet (decision 18).
5. **A hard cap, ten by default, that the human can set.** A whole-number setting in `.ctoc/settings.json`, declared in the settings schema in `src/lib/settings.js`, limits the number of **critiques run per open**. Its default is 10 (decision 21), so the limit applies from the first open with nothing set. One critique is one lone plan or one whole parent group, all-or-nothing, because lenses without their synthesizer produce nothing a human can read. The remainder is reported as "N not yet critiqued" (critiques, with the number of plans they cover), rendered on the dashboard where the pending-decision count is rendered and in the session-start directive, and the references are available on request. Nothing is silently skipped, and **the count is rendered in the same unit of work that produces it** (the stale scan's unrendered `unreadCount` is the recorded example of an honest signal nobody sees). An absent setting gives 10; a value that is not a whole number of zero or more gives 10 and is reported as unreadable, never "no limit"; zero is a legitimate value that stops the fleet and reports every candidate as not yet critiqued.
6. **Order and side effects are unchanged.** Candidates keep the existing critical-first, furthest-along-first order (they come from `pendingGateDecisions`, which can also cross plans at the pre-build moments as a side effect; nothing here changes that). Review plans are removed from the candidates after that list is produced; `pendingGateDecisions` itself keeps listing them as decisions awaiting the human.
7. **A refused review plan is not a critique input, because nothing at review is critiqued.** The done check's refusal (no verify evidence, a failed run, stale evidence) is shown as a mechanical fact exactly as today and holds nothing in a queue. `pendingGateDecisions` already carries `passesValidation` per plan; this plan does not change how it is used at the pre-build stages.
8. **The fleet is an instruction, not a fence.** The session model executes the dispatch. Code can shape the list the model is told to dispatch and the count it is told about, and it can render the remainder; no hook sees the model's launches except the slot fence in `PreToolUse.Task.js`.

## 3. CAPTURE — Acceptance Criteria

Each criterion is one runnable check. Given/When/Then, with concrete values where they exist.

### Part A — the three paths

1. **Direct: a rename whose callers the suite finds.** GIVEN the request "rename the exported function `formatRow` to `renderRow`; its callers are in two library files and the suite", the three source files exist and are on none of the trust-boundary sources, the export set changes only by that one removal and that one addition, no file is added, and no test assertion is named as needing to change, WHEN the executor proposes those files, THEN the classifier reports path direct with each signal and its source; no plan file is created; the edit hook allows edits to those files and to no other; the affected tests run green before the edit; the full gate runs after it; the diff review runs once; the commit and patch bump happen only when the gate passed and its evidence is newer than every listed file; the human sees the announcement line and the milestone line. The same holds for an internal helper renamed inside one file. A caller the suite does not reach fails the gate and nothing is committed (criterion 9).
2. **Direct: a patch-level dependency bump.** GIVEN the request to bump one dependency from `1.4.2` to `1.4.3` in `package.json`, WHEN classified, THEN the path is direct. GIVEN a minor bump or a new dependency, THEN the path is full.
3. **Quick: a new optional field with stated semantics.** GIVEN the request "add an optional `label` option to `renderRow`; when present it is printed before the row; behaviour without it is unchanged", one module, one test file, WHEN classified, THEN the path is quick; the record lists the source file and the test file; the change set must include a test file at finish (an empty test list on the quick path refuses the commit and reclassifies); the full gate and the diff review run; the human is asked "finished?" with the diff summary, or sees a status line under an active keep-going batch.
4. **Full without a question: a hook.** GIVEN any request whose proposed files include `src/hooks/PreToolUse.Bash.js`, WHEN classified, THEN the path is full, the deciding signal is named (trust boundary), no question is asked, no record is written, and the edit hook's behaviour for that file is exactly today's except that a typed escape phrase no longer allows it (criterion 29).
5. **Mixed signals: one question, flat.** GIVEN a request whose signals disagree (one green signal set and one signal with no source that the request needs), WHEN classified, THEN CTOC names the deciding signal and asks once; the question offers "plan it" and "just do it", states each consequence in plain words, and contains no recommendation marker.
6. **Override down on the trust boundary is refused.** GIVEN a request touching `src/hooks/human-gate-check.js` and the human types "just do it", THEN the classifier refuses, states that the trust boundary is never overridden down, records the refusal, and the path stays full. No record is written.
7. **Override up.** GIVEN a change classified direct with an open record and the human types "plan it", THEN the path becomes full, the record is closed as superseded, no further edit is covered by it, and a functional plan is created through the existing route.
8. **An agent typing the words changes nothing.** GIVEN a transcript in which "just do it" appears only in an assistant message and a tool result, WHEN the classifier reads it, THEN the classification is unchanged and the log records an ignored override with the role it appeared in.
9. **A failing gate is not committed.** GIVEN a direct change whose full gate fails, THEN nothing is committed, the failure is reported in plain words with the evidence, the record stays open, and the commit gate refuses until a fresh passing run exists.
10. **The grant is exact.** GIVEN an open record listing `src/lib/a.js`, THEN an edit to `src/lib/a.js` is allowed by the edit hook and a determinate shell write to it is allowed by the shell hook; an edit to `src/lib/b.js`, or a shell write to it, is refused on both channels with today's message.
11. **A quick change that needs a second module stops.** GIVEN a quick record listing one module and an executor that discovers it must change a second, WHEN it writes to the second file, THEN the hook refuses; the executor files the scope-growth question naming the record; nothing is committed or reverted; on the human's answer the path becomes full, the record is closed as superseded, and the plan is created then. At finish, growth inside a listed file (a new export not in the request, a new dependency) stops the change the same way.
12. **The grant cannot be forged.** (a) An editing-tool write to the record directory is denied at every mode. (b) An inline evaluation that touches the record directory or the record module is denied by the shell hook. (c) A record whose request fingerprint matches no message the human typed in this transcript grants nothing, and the edit falls back to today's behaviour. (d) A record from an earlier session grants nothing.
13. **Nothing absolute weakens.** GIVEN an open record and each of the following, THEN each is refused exactly as today: a write to the approval ledger; a write to the verify evidence store; a write under `.ctoc/streaming/` outside its quarantine; an edit to a command table without an approved plan; an edit to any trust-boundary file under a light record or under a typed escape phrase; an irreversible command; a raw move of a plan file. The shell hook's coverage decision is identical at strict, soft and off.
14. **The commit gate reads evidence.** GIVEN a light-path commit with no evidence, failed evidence, or evidence older than any listed file, THEN `git commit` is refused with the reason. GIVEN fresh passing evidence, THEN it is allowed. `git push` still needs the human's word.
15. **Unknown is not green.** GIVEN a request in a stack whose signals the classifier cannot measure, THEN the path is never direct, and the announcement says which signals had no source.
16. **The announcement is visible before the first edit and uses plain words.** THEN it names the path, the files, the deciding signal, and how to override; it contains no gate number and no internal code; the fence over instruction text (`instruction-gate-words-fence`) passes on the new reminder and recipe text.
17. **The measured signals are used, not re-implemented.** THEN the one trust-boundary list calls `isProtectedEnforcementPath` and the four exported guards and reads `.ctoc/config/refinement-triggers.yaml` at call time (no copied list), adding only the named files of decision 20; the classifier and the typed-phrase check both call that one list; the export comparison calls `analyzeExports`; and the risk surface reads the same triggers file. Shown by running, not by searching text: changing the triggers file in a fixture changes the verdict of both callers.

### Part B — the critique fleet

18. **Todo with 137 approved slices: zero dispatches.** GIVEN a pipeline with 137 approved slices in todo and nothing else pending, WHEN the dashboard opens and when a session starts, THEN the candidate list is empty, the session-start directive is empty, and no fleet task is recorded.

GIVEN one changed byte, THEN the plan is a candidate again. GIVEN a questions file with no fingerprint (every file on disk today), THEN today's modification-time rule decides.

25. **The cap is honest, and it is 10 until the human changes it.** GIVEN no cap setting in `.ctoc/settings.json` and a fixture of 12 candidate critiques, THEN 10 are dispatched and 2 are reported as not yet critiqued. GIVEN the setting at a value that is not a whole number of zero or more (the text "ten", -1, 2.5), THEN 10 apply and the dashboard says the setting could not be read. GIVEN the setting at 0, THEN none is dispatched and all 12 are reported. In each case the dashboard and the session-start directive state the count, the references are available on request, and the count is the difference between candidates and dispatched, computed, not remembered. A critique already queued, running or waiting in the quarantine is not dispatched again and is not counted as dispatched by the new open.
26. **Plans at the finished decision are never critiqued.** GIVEN plans in review, some the done check refuses and some it passes, THEN none is a candidate, none is counted in the "not yet critiqued" remainder, no fleet task is recorded for any, and the done check's refusal reason is shown exactly as today. The on-demand `discuss` and `discuss-all` are unchanged.
27. **The lenses at a pre-build decision.** GIVEN a plan at the "what to build" or "how to build it" moment, THEN the recipe dispatches the premortem, the devil's advocate, the red team and the advocate, then the synthesizer; the attestation the synthesizer writes lists all four as having run; the recipe text, the directive text and the two agent definitions name the same four.
28. **The human's flow at the finished decision is intact.** GIVEN a review plan with passing recorded evidence and no question file, WHEN the human opens the finished decision, THEN it is presented as a decision awaiting him with the done check's result, nothing waits on a critique, and only the human's word moves it to done. GIVEN a review plan that still has a question file from before this change, THEN that file neither makes the plan a candidate nor blocks its presentation.

### Trust boundary — the typed phrase and the one list (decisions 19 and 20)

29. **A typed escape phrase never unlocks a trust-boundary file.** (a) GIVEN each of the seven typed phrases (hotfix, trivial fix, trivial change, quick fix, urgent, skip planning, skip iron loop) typed by the human in the transcript, no approved plan covering the file, and the mode at strict, WHEN an editing-tool write targets `src/hooks/PreToolUse.Edit.js` or `src/lib/escape-phrases.js`, THEN the edit hook blocks it and the reason names the trust boundary and says an approved plan is needed. (b) GIVEN a determinate shell write to either file, THEN the shell hook denies it at strict, soft and off. (c) GIVEN the same phrase and an ordinary source file off the trust boundary, THEN today's behaviour holds and the write is allowed. (d) GIVEN the mode at soft or off, a boundary file and no covering plan, THEN the edit channel decides exactly as it does today with no phrase typed, because this plan changes what the phrase unlocks and not what the mode relaxes. (e) GIVEN a boundary file covered by an approved plan, THEN it is allowed as today; GIVEN `.ctoc/settings.json`, which the whitelist allows ahead of every later check, THEN behaviour is unchanged (see Findings).
30. **One list, driven by both callers.** (a) GIVEN each of these paths — a file under `src/hooks/`, `src/lib/plan-coverage.js`, a path under the approval ledger directory, one under the verify evidence directory, one under the streaming store, `.ctoc/quality-config.yaml`, a path matching a glob in the triggers file, each of the seven named files of decision 20 (`.claude-plugin/hooks.json`, `src/lib/escape-phrases.js`, `src/lib/enforcement-mode.js`, `src/lib/state-manager.js`, `src/lib/step-13-verify.js`, `.ctoc/settings.yaml`, `.ctoc/settings.json`), and the new trust-boundary module itself, WHEN the classifier and the typed-phrase check are each driven with it, THEN both report boundary. (b) GIVEN an ordinary file such as `src/lib/format-row.js`, THEN both report not boundary. (c) `isProtectedEnforcementPath` returns, for a fixed set of paths, exactly what it returns today, so plan coverage's meaning is unchanged. ## Scope

### In Scope

- The intake classifier, its signals, decision rule, override words and the red line (criteria 1 to 9, 15 to 17).
- The light-path record, its sanctioned writer, its protected directory, the grant in both hooks, the commit gate's evidence check, and the growth stop (criteria 10 to 14).
- The path-aware routing directive replacing the constant one.
- The one trust-boundary list in one new module, used by the classifier and by the typed-phrase check, and the change that a typed escape phrase never allows a trust-boundary file on the edit channel or the shell channel (criteria 29 and 30).
- The fleet's eligibility (the two pre-build stages only), grouping, idempotence, the default cap of 10 with its setting and remainder count, and the directive and recipe text that carry them (criteria 18 to 28).
- The content fingerprint stored with the questions and used for the critique's freshness only (criterion 23(b)).
- Answer fan-out to the members of a group, in `src/lib/streaming-gate.js`, and the group promotion in the sweeper, without changing how "answered" is encoded.
- The settings-schema entry for the cap, with its default of 10.
- The `CLAUDE.md` sections that describe the pipeline and the enforcement flow, updated in the same unit so the contract matches the code.

**Not verified.** It is not verified against the hook body, and the write, multi-edit and notebook-edit hooks were not opened, so it is not known whether another hook or a later check denies it. I have not rated its severity, because it is not confirmed.
