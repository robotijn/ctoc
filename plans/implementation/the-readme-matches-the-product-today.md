A dead or wrong link is corrected or removed. A number with no measurement behind it is removed.

5. **The structure is the human's.** The README has the structure under "The structure of the rebuilt README" and the style requirements above. The rebuild keeps every shape the release sync matches and every need `syncToReadme` has, and that is proven (criterion 27).

### How a capture is taken and proven real

1. **A disposable project, outside the repository.** For the first-run screen and the empty-pipeline screens, a fresh project is made the way the quickstart describes (a package file and one source file). For the busy-pipeline screens (the dashboard, the decision screens, the task board), the data comes from one real run on a disposable copy of this repository's own pipeline state (recorded under Decisions Taken Under Ambiguity). Either way the working directory of every capture run is disposable and is never this repository. The record states which root the product was given, and, for the copy, when it was taken and what was copied.
2. **The bytes come straight from the program.** The real command is run and its output goes to a file by redirection — never through anyone typing it. The record keeps, per capture: the exact command line, the disposable project's description, the exit code, the byte count, and a content checksum of the raw output. The raw output files are kept beside the record.
3. **A closed list of transformations, applied mechanically.** The README block is the raw output after the recorded transformations (a path shortened to a placeholder; a long body elided with a visible marker naming what was cut) and nothing else, apart from the dashboard capture's version line that the release sync keeps current. A throwaway program applies the recorded transformations to each raw file and compares the result byte for byte with the fenced block in the README. Its printed result and the transformation list go into the record, so a second reader can redo the comparison with a program of their own. A block that does not match is wrong and is replaced.
4. **Content that comes from an agent's earlier work says so.** A screen that shows something an agent wrote earlier (a precomputed question with its pros and cons, a plan body) states in the README whether that content is real agent output from a real plan or sample data written for the page and rendered by the real screen code. Real rendering of authored data is not the same thing as real agent output, and the page does not blur them. Where the copied pipeline state holds a precomputed question, it is real critique-fleet output from a real plan of this repository, and the README says so.
5. **The real pipeline is proven untouched.** Before the first capture run and after the last, the pass lists every file under the real repository's plans folder and pipeline-state folder with a content checksum (append-only logs excluded). No plan file may have moved or changed, and no pipeline-state file may have been written, because of a capture run. Any difference is named and attributed to its cause; a difference caused by a capture run fails the pass.
6. **What this proves, honestly.** It makes hand-typing detectable, not impossible: a forger would have to forge the raw file and its checksum too. The protection is that a second reader can check: they take a fresh copy of the pipeline state and confirm that the same blocks, labels, order and wording appear with different values. The bytes of a busy-pipeline capture are not regenerable, because this repository's state moves; the record states when the copy was taken.
7. **A stage with no screen of its own.** Each stage section's "What you see" is a real capture of a screen the product shows at that stage. Where the product shows nothing at a stage beyond the dashboard's row for it or the empty stage list, the section shows that real capture and says so; it never shows an imagined screen.

### How a claim is checked

- **The census comes first.** The pass reads the pre-pass README piece by piece (see "Carried word for word or rewritten") and lists every sentence that asserts a number, a behaviour of the product, a file name, a command, a setting, a link, or something about another product or standard. That list is the claim inventory. Sentences that only instruct or explain, with nothing checkable in them, are not claims; each piece's record states how many such sentences it held and of which kind, so the classification can be disputed. Text the rebuild writes new (headings, the three-part frames, the why sentences) is read the same way and each of its claims gets a row.
- **Six methods, one per row, none by word search alone.** (1) Ran: the real command or hook was run in the disposable project and its output recorded. (2) Read: the source lines that decide the behaviour were read and are quoted with their path. (3) Counted: measured on disk by a real walk, with the number printed. (4) Fetched: an external web address was fetched today and the observed status and page title recorded. (5) Documentation: the live official documentation of whoever owns the claim was read — the host's for a claim the host owns (installing the plugin, updating it, the plugin menu path), and each other product's own for a comparison-table cell, found by live web research and cited with the date checked. (6) Test named: where the README says a test enforces something, that test was run and passed.
- **Four verdicts, closed.** True, corrected, removed, not verified. A row without a verdict is a gap. A claim marked not verified is marked in the README where it stands, in plain words. A comparison-table cell about another product takes only true, corrected or removed: a cell that cannot be verified is removed, not marked.
- **A claim about how the skill library was built** (the improvement loop the README describes today) is checked against the commit history and the plans that did the work. What the history cannot show is marked not verified, until Part B's record replaces it.
- **A "why" is a claim.** Each sentence saying why a step exists carries a row: the run or the source lines it rests on.

### Carried word for word or rewritten — the test that decides

The human's instruction of 2026-09-29 — "rebuild the readme completely if needed" — was made concrete by the two later ones: the README is rebuilt in its structure, and the tests below do not decide that. What they still decide, piece by piece, is whether TRUE text in the pre-pass README is carried over word for word into the new structure or must be rewritten. Their inputs are the rows the pass already produces. A piece's verdict is decided only after every claim row and capture row of that piece carries a verdict, because a share cannot be read from a partial set of rows.

**What a piece is.** The text under one heading of the pre-pass README; in Part 2, one recipe (a paragraph with a bold lead); the lead paragraph; the reading guide. The census fixes the list from the pre-pass README, which the record names by commit and content checksum, and every sentence of it belongs to exactly one piece. Two pieces are removed by the human's instruction and get no verdict: the reading guide with its course table, and the design section about course-design literature. The record still gives each a row saying so.

**What a row counts as.** A row is a claim row or a capture row; sentences that only instruct or explain are not rows. A claim row is either true or not true (corrected, removed, or not verified — each of those three needs a change to the text). A capture row is true when the old block and the real output have the same blocks, labels, order and wording, differing only in values the README labels as a moment (counts, plan names, the version); it is replaced by the fresh capture either way. A capture row is corrected when they differ in a block, a label, the order or the wording.

**The share test — applies to every piece.** The piece is rewritten when its rows that are not true strictly outnumber its rows that are true. A piece with no rows cannot fail it.

Why this threshold and no other: the record holds counts of rows by verdict and nothing else on which a threshold could rest, so the only threshold that needs no invented number is the majority. Below it, the true rows are the larger part of the piece, and rewriting would churn true text, which the standing requirements forbid. Strictly above it, the true rows are the minority, and a patched piece would be a few old sentences scaffolding around mostly new ones — a rewrite in all but name. A tie keeps the text. This is a rule for deciding, not a claim about what is optimal. For a piece of very few rows the two outcomes can produce the same text; the record still says which one it was.

**The flow test — applies to a piece that tells the reader to do things in an order or shows screens in an order (the old lessons and recipes).** The pass runs the piece's steps in the disposable project, reading the host's live documentation for the host-owned steps, and lists two things in order: (i) the steps the piece tells the reader to take, and (ii) the blocks of each screen the piece shows. It lists the same two things as the product really did or the documentation really shows. The piece is rewritten when the two lists differ in membership or order: a step the product does not have, a step the piece omits, a step at another position, a screen block the piece lacks or has that the product does not, or blocks in another order. A step under a different name that does the same job at the same position, or a different value, is a difference of wording and does not fire this test; it is a corrected row and is patched. A host-owned step the documentation does not show is marked not verified and neither fires nor passes this test. The sequence of the NEW structure is checked separately, by criteria 28 and 29.

Both checks can be redone from the record: the share test by counting the piece's rows by verdict, the flow test by comparing the two ordered lists the record holds for the piece.

**The piece verdict** is one of three, a closed set that is separate from the four claim verdicts (a fifth claim verdict would let a row hide):

- **Left as it is** — every row is true. The piece's prose is carried into its new home word for word; its capture blocks are replaced by the fresh captures as the capture rules require.
- **Patched** — at least one row is not true and neither check fires. The piece is carried into its new home with each corrected, removed or marked row applied in place, and every other character of the carried text is unchanged.
- **Rewritten** — at least one check fires. The piece's content is written afresh in its new home from what the real product does, not by editing the old sentences. Its captures are re-taken by the capture rules, its claims are checked by their methods, and each of the new text's claims gets its own row.

**The rebuild.** Because the structure is the human's, the moving is done by the new structure: a carried piece is moved or re-linked only where the new structure requires it, each such change named in the record, and true text is never re-worded for style, even in a rebuild. The counts of pieces carried word for word, carried with in-place corrections, rewritten, and removed by instruction go into the record for information. The earlier test that applied the share test to the whole README to decide whether to rebuild it is retired: the human's instructions decide that.

## 3. CAPTURE — Acceptance Criteria

Behaviour, each one checkable from the record and from `npm test`.

**Part A — the truth pass**

1. GIVEN a fresh project with an empty plans folder and the plugin installed from the marketplace, WHEN the builder follows the quickstart step by step and then reads each stage section, THEN every screen shown has the same blocks, labels, order and wording as the real screen, the only differences being values the README labels as a moment (counts, plan names, the version), AND every command, word and option a step tells the reader to use exists in the product under the name the README gives it. 2. GIVEN a capture whose real output differs from the README block in a line the prose does not explain (today: the line about a plan whose builder is no longer running, re-queued for a clean rebuild and re-verification), WHEN the pass compares, THEN the block is replaced by the real output, the prose beside it gains an explanation of that line taken from reading the source that prints it, and the record row shows the old block, the new block and the verdict corrected.
3. GIVEN a capture whose content came from an agent's earlier work, WHEN it is presented, THEN the README says whether that content is real agent output or sample data rendered by the real screen code, and the record row says which.
4. GIVEN a sentence that states how the product behaves, WHEN the behaviour is run or its deciding code path is read and the result contradicts the sentence, THEN the sentence is corrected to the observed behaviour (or removed if it cannot be stated truthfully), and the row shows the old sentence, what was run or read, what it printed, the new sentence, and the verdict corrected.
